System Overview

This system simulates a real-world bank's Credit Limit Management and Earmarking process across multiple partner services. It demonstrates how a facility request flows through various approval stages, with rules-based decision making, pool management, and multi-protocol messaging.


Core Objectives

  • Real-time limit check & earmarking
  • Multi-stage pipeline visualization
  • Complex rule engine for approvals
  • Dual database (MongoDB/PostgreSQL)

Key Technologies

  • Apache Camel (Orchestration)
  • Kafka & IBM MQ (Messaging)
  • Java Faker (Data Generation)
  • React (Visualization)

Approval Rules Engine

The system employs a multi-tiered rule engine to determine the approval path based on risk rating and amount.

Category Threshold Risk Action
Auto-Approve < $100k <= BBB SYSTEM APPROVE
Single Sign-off < $1M <= BB CREDIT MANAGER
Dual Sign-off < $5M <= B HEAD OF CREDIT
Committee > $50M Any BOARD RISK

DSL Configuration (YAML)

rule_single_approval:
  condition: amount < $1,000,000 AND risk_rating <= BB
  action: REQUIRE_SINGLE_APPROVAL
  authority: RELATIONSHIP_MANAGER

rule_dual_approval:
  condition: amount >= $5,000,000 OR risk_rating > B
  action: REQUIRE_DUAL_APPROVAL
  authority: [CREDIT_MANAGER, HEAD_OF_CREDIT]

The architecture leverages Apache Camel for orchestration, using Kafka for internal event streaming and IBM MQ for enterprise partner communication. Persistence is handled by a polyglot approach: MongoDB for the event store and PostgreSQL for transactional limits.
